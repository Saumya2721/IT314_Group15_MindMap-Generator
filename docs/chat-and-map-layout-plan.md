# Implementation plan for map spacing, branch edits, and chat explanations

## 1. Fix generated map spacing first

**Finding.** The generation callback in `backend/app/routes/internal.py` calls `compute_layout` in `backend/app/services/generator.py`. The function places first-level branches on a radius of 240 and their children on a radius of 160 within a 0.6-radian arc. With four siblings, adjacent centers are only about 24 canvas units apart. All nodes deeper than grandchildren enter a diagonal fallback, irrespective of parent. A single nonzero coordinate can also skip layout for the entire graph. React Flow then accepts most of those coordinates. Its active adapter, `frontend/src/utils/graphAdapter.js`, also treats a valid position on either zero axis as missing. Zooming out cannot separate intersecting cards.

**Implementation sequence**

1. Establish the actual rendered footprints of root, branch and concept cards, including wrapped labels, handles and margins. Use the same size contract in layout and rendering. If a card can grow beyond its predicted footprint, measure it before final placement or constrain its displayed size and keep its full content in the inspector.
2. Replace the two-ring layout with a deterministic left-to-right tree layout for every depth. Compute subtree heights bottom-up using card heights and a constant sibling gap. Allocate disjoint vertical bands top-down, center each parent over its children, and space depth columns by the widest card in the preceding column plus an edge gutter. Keep sibling order stable across reloads. Allocate separate bands for disconnected components. For multi-parent maps, select a stable spanning forest for placement and retain every original edge for rendering. Guard traversal against cycles in legacy input.
3. Align React Flow handles and edge routing with the layout direction. Reserve room for relationship labels and fan-out. Check representative dense trees for edges passing through unrelated cards or labels covering cards. Cross-links may still cross on arbitrary user-edited graphs.
4. Integrate placement at persistence boundaries. Lay out an entire new map before saving it. For branch regeneration and accepted chat additions, retain the branch anchor and place new nodes against the occupied bounds of the **whole** map. Move only the affected generated region when possible. Save coordinates and graph changes atomically under the existing version check. Use the same stored geometry for editor, history and export. Fit the viewport after the first layout, and keep the user's pan and zoom on subsequent chat edits.
5. Represent missing placement explicitly for new data. Preserve valid axis positions and manually dragged nodes. Give older overlapping maps an explicit **Arrange map** action with undo or snapshot recovery. Opening an old map should preserve its saved arrangement. Update the active graph adapter and its tests. The separate `frontend/src/utils/layout.js` is not the adapter imported by the editor.

**Acceptance.** Cover a single node, a wide shallow tree, an unbalanced six-level tree, a 70-node map, long labels, mixed stored and missing positions, and a multi-parent map. Assert zero pairwise card intersections after initial layout and after expanding a branch beside another branch. Check minimum gaps using rendered bounding boxes at a common zoom. Verify stable positions on reload, correct zero-axis handling, preserved dragged nodes, and agreement between saved positions, history and exported output. Open a freshly generated dense map in the browser and read a branch without dragging any cards.

## 2. Make an edit followed by an explanation a single user workflow

**Finding.** In `llm/mindmap_llm/chat/intents.py`, correctly spelled “expand the branch and explain the additional details” already matches the branch rule. “Exppand” misses that verb rule and can reach a classifier whose fallback is a question. The classifier receives the current message and map snapshot. The proposal builder subsequently asks a model to choose the action type again. These are separate opportunities to lose the user's request. A successful branch classification alone does not establish that the proposal targeted the right node, was accepted, or changed the map.

1. Trace one turn from chat submission through classification, target resolution, proposal, confirmation and completion. Capture the route, target resolution outcome and resulting graph delta in tests. Use the exact reported message both with and without a selected branch.
2. Pass the selected node ID as optional context through the UI, API and mirrored worker contracts. Resolve an explicit unique node reference first, then a valid selection for “this/the branch”, then an unambiguous recent reference. When multiple candidates remain, return a short clarification with clickable branch labels. Revalidate membership against the current map.
3. Teach the classifier to distinguish a **graph change** (“give this branch two more subtopics”) from a **conversational explanation** (“expand on your explanation”). Recognize common spelling variants in action context, handle negation before verb shortcuts, and preserve an accompanying request to explain. Constrain the proposal builder to the resolved operation and scope. An ambiguous edit should reach clarification even when the decision provider is unavailable.
4. Treat “expand” as additive. Reuse the existing branch elaboration and create-node/create-edge proposal machinery in `chat/expansion.py` where applicable. Ground additions in branch context, deduplicate against existing children, and preserve existing node IDs, annotations and edges. Reserve subtree replacement for explicit rewrite/regenerate requests. In `orchestration/prompts.py`, distinguish additive instructions from replacement instructions at their callers because initial generation and branch refinement share builders.
5. Keep the existing proposal confirmation. Preview the target and proposed additions. After successful application, answer the explanatory clause from the committed graph delta and its sources, using the final node IDs. A rejected, stale or failed change should show its actual outcome. A retry must not append the same children twice.

| User input | Acceptance outcome |
|---|---|
| “Exppand the branch and explain the additional details”, with a selected branch | One additive proposal. Accept adds linked children and explains them. Decline preserves the graph. |
| Same request with several plausible branches and no selection | Ask which branch and resume the original compound request after selection. |
| “Expand on your explanation of photosynthesis” or “Explain this branch without changing it” | Grounded prose, no proposal. |
| “Add two examples under Storage” with a different node selected | The uniquely named Storage branch receives the proposal. |
| “Regenerate the whole map” | Existing whole-map confirmation and regeneration path. |

## 3. Make grounded chat explanations readable and links dependable

**Finding.** In `llm/mindmap_llm/chat/prompts.py`, the QA prompt requests concise answers, mandates a UUID tag on every node mention and explicitly encourages tables for structured summaries. In `chat/qa.py`, the default QA output budget is 2,048 tokens. In `frontend/src/components/canvas/ChatPanel.jsx`, a tagged unresolved ID can become a button displaying its hexadecimal prefix. Bare IDs receive special link treatment only when found in the node lookup.

1. Change the QA prompt to lead with a direct answer in prose. For “explain”, describe how or why the concept works, connect it to the relevant branch, and give one example or consequence when supported. Use ordered steps for a process and a table for an explicit table request or a genuine side-by-side comparison. If the sources support only a definition, give that definition and identify the missing detail. Add short paired examples to the prompt evaluation set.
2. Link the first meaningful mention of a node using the canonical label and tag. Use its plain label for repeats. Resolve citations against the snapshot before returning them and against the current map when rendering chat history. Normalize a known bare node UUID to a labeled link. Render an unresolved reference as its available label or “unavailable node” with no jump action. Preserve source numbers, math, code and unrelated technical identifiers.
3. Keep the current token setting as the first evaluation baseline. For detailed questions, prioritize the target, relevant neighbors and retrieved evidence in the input budget. Reserve output space against the active model limit. Record answer length and provider truncation status when available. If grounded answers still end early, tune a separate bounded detailed-answer budget or offer continuation from the last complete point. Avoid increasing the budget for greetings and short factual answers.

**Acceptance.** Run representative explanation, comparison, thin-evidence and low-budget turns. Score whether each answer addresses the question, explains a supported relationship or mechanism, and cites the relevant evidence. Ordinary explanation fixtures should produce prose. Explicit table requests should render a table. Test known, stale, malformed and repeated node references in paragraphs, lists, tables and reopened conversations. Every active node link must focus the correct card. Historical references must remain readable after regeneration.

## Delivery and verification

Ship geometry first because it affects every newly generated map. The chat explanation and routing changes can be developed independently. Integrate them with a browser scenario that generates a dense map, selects a branch, sends the typo-containing compound request, accepts the proposal, follows a link in the explanation, and reloads the map. Use deterministic worker/API/UI fixtures for regression coverage and a small live-provider sample for language quality. This plan is based on source inspection. Browser geometry measurements and live model outputs are implementation checks still to perform.
